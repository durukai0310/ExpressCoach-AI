## <a id="p0-fatal"></a>P0 致命问题 (导致 crash 或完全不可用)

### P0-1: DeepSeek API Key 无效 → 整条链路中断

| 项目 | 内容 |
|------|------|
| **Day** | Day 1-7 (横跨整个 W1) |
| **现象** | 运行 `node src/index.js` 始终报 `401 Unauthorized`，任何 API 调用都失败 |
| **影响** | 意图识别 / 关系判断 / 三版本生成 全部无法工作 |

| **预防措施** | 在 `index.js` 的 `main()` 中增加 API Key 存在性检查，启动时给出明确提示 |

### P0-2: SOUL.md 文件缺失 → `process.exit(1)` 直接崩溃

| 项目 | 内容 |
|------|------|
| **Day** | Day 7 |
| **现象** | 启动时若 `SOUL.md` 或 `soul/xxx.md` 文件路径错误或缺失，程序直接调用 `process.exit(1)` 退出 |
| **影响** | 用户看到 crash，没有降级手段 |
| **根因** | `loadFile()` 函数中 `process.exit(1)` 过于激进 |
| **解决办法** | 改为 `return null` + 调用方做降级处理。关系判断/三版本在 SOUL 不可用时输出默认回复 |
| **代码变更** | `loadFile()` 从 `process.exit(1)` → `return null` + 颜色标记 |

### P0-3: LLM JSON 解析失败时没有降级 → 输出 undefined

| 项目 | 内容 |
|------|------|
| **Day** | Day 7-8 |
| **现象** | DeepSeek 偶尔返回非 JSON 格式（markdown 包裹或纯文本），`parseResponse()` 返回 `null`，导致后续代码输出 `undefined` |
| **影响** | 意图识别/关系判断输出的 `parsed` 为 `null`，格式化输出显示 "(生成失败)" |
| **根因** | 仅有单层 `JSON.parse`，没有 markdown 和 fallback 提取逻辑 |
| **解决办法** | Day 7 增强 `parseResponse()`：先试 `JSON.parse` → 失败后正则提取 ` ```json ``` ` 代码块 → 再失败提取最外层 `{}` → Day 8 增加 `fallbackRecognize()` 关键词兜底 |
| **代码变更** | `parseResponse()` 3 层提取 + `fallbackRecognize()` 规则库兜底 |

### P0-4: 意图分类与项目大纲不一致

| 项目 | 内容 |

## <a id="p1-serious"></a>P1 严重问题 (功能可用但存在缺陷)

### P1-1: Promise.all 单点故障 → 一个版本失败全部丢失

| 项目 | 内容 |
|------|------|
| **Day** | Day 10-11 |
| **现象** | 三版本并行生成用 `Promise.all`，若温和版 API 调用失败，坚定版和高情商版的结果也全部丢弃 |
| **影响** | 单次 API 超时/失败导致整个三版本步骤失败，用户体验极差 |
| **根因** | `Promise.all` 的 fail-fast 特性：任意一个 reject → 全部 reject |
| **解决办法** | Day 11 改为 `Promise.allSettled`：对 rejected 的版本构造降级占位结果 (`isDegraded: true`)，已成功的版本不受影响 |
| **代码变更** | `generateThreeVersions()` `Promise.all` → `Promise.allSettled` + 单点降级占位 |

### P1-2: Jaccard 重试也用 Promise.all → 失败同上

| 项目 | 内容 |
|------|------|
| **Day** | Day 11 |
| **现象** | Jaccard 差异度检查后的重试阶段也用 `Promise.all`，重试失败会丢弃已成功的版本 |
| **解决办法** | 同样改为 `Promise.allSettled`，失败的重试保留原版本 |

### P1-3: 关系判断规则与 LLM 一致性低 (40%)

| 项目 | 内容 |
|------|------|
| **Day** | Day 9-11 |
| **现象** | 10 个场景中，规则词典匹配与 LLM 精调在 6 个场景中命名不一致（如 "上级" vs "上下级"、"父母" vs "家人"），导致误判为"不一致" |
| **影响** | 混合模式的可信度在日志中看起来比实际低 |
| **根因** | 规则词典中 `type` 字段命名（如 "上级"）与 LLM 自由输出（如 "上下级"）不是同一词汇体系 |
| **解决办法** | 确认为设计意图 ≠ bug。规则是参考锚点，LLM 有权纠偏。在 Day 12 社交计算报告中确认 4 维度值 100% 一致（命名差异不影响最终策略选择） |

### P1-4: Day 11 代码 Review 发现 recognizeIntent 断网会 crash

| 项目 | 内容 |
|------|------|
| **Day** | Day 11 Review |
| **现象** | `recognizeIntent()` 中若 `callDeepSeek()` 抛出异常（断网/超时），异常直接向上冒泡 → `runAnalysis()` 的 catch 收到后 `throw new Error` → 全流程崩溃 |
| **影响** | 网络不稳定时整个程序不可用 |
| **根因** | `recognizeIntent()` 没有 try/catch 包裹 API 调用 |
| **解决办法** | Day 11 在 `recognizeIntent()` 内增加 try/catch → 捕获异常后调用 `fallbackRecognize()` 降级 |

### P1-5: 三版本长度不均匀

| 项目 | 内容 |
|------|------|
| **Day** | Day 10 |
| **现象** | 坚定版普遍偏短 (76-84 字)，温和版和高情商版 120-150 字 |
| **影响** | 用户可能觉得坚定版质量不够 |
| **根因** | `generator-firm.md` 中"简洁有力"指令过于强调 |
| **解决办法** | Day 10 调整 SOUL.md: 温和版和坚定版增加"回复内容应充实完整，不少于80字"的提示 |

### P1-6: 全流程耗时超标 (7.3s vs 5s 目标)

| 项目 | 内容 |
|------|------|
| **Day** | Day 10-12 (持续) |
| **现象** | 10 个场景平均 7.3s，最慢 8.0s，超 5s 目标约 46% |
| **影响** | 性能报告显示 ⚠️ 警告 |
| **根因** | 三步串行 API 调用（意图 → 关系 → 三版本），每次 1-2s 网络延迟。三版本虽是并行但 3 个 API 都在等最慢者 |
| **解决办法** | 短期 (W3): 意图识别和关系判断可并行执行（无依赖）。中期: 高频场景缓存 (5min TTL)。长期: 小模型本地部署意图识别 |
| **状态** | ⚠️ 已知局限，已记录弱点分析 |

### D21-B1 (P1): M5 `predictReactions is not a function`
