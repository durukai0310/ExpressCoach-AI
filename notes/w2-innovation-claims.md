## 不可替代点 1: 三版本策略分化

### 问题
通用 LLM 在单次对话中只输出一种回复。用户需要反复 prompt 才能获得不同风格的版本。而且无法保证风格差异度——temperature 调高≠策略分化。

### ExpressCoach 的方案
**三 Agent 并行生成** 使用三份独立 SOUL.md（温和/坚定/高情商），每份有独立的策略定位和 Few-shot 示例，配合 **Jaccard 文本相似度自动检查** 确保输出不会趋同。

### 测试证据

**场景: "我想拒绝朋友借钱但不想伤感情"**

| 指标 | 温和版 | 坚定版 | 高情商版 |
|------|--------|--------|---------|
| 核心策略 | 情感共情优先 | 立场明确 + 边界设定 | 信任建立 + 替代方案 |
| 字数 | 128 | 97 | 145 |
| 开头方式 | "你愿意跟我开口..." | "我理解你现在需要钱..." | "兄弟，你能开口..." |

**Jaccard 差异度**:
| 对比组 | 相似度 | 判定 |
|--------|--------|------|
| mild-firm | 0.185 | ✅ 差异化显著 |
| mild-eq | 0.372 | ✅ 差异化 |
| firm-eq | 0.200 | ✅ 差异化显著 |

**为什么通用 LLM 做不到**:
- ChatGPT 的 `temperature` 参数只能增加输出的随机性，但不能保证策略层面的分化
- 三份独立 SOUL.md 的策略差异是 **结构性的**（策略目标不同），而非随机的
- Jaccard 自动检查 + 重试机制是 **工程化保障**，通用 LLM 没有这个闭环

## 不可替代点 2: 关系感知生成

### 问题
通用 LLM 对所有对话对象一视同仁。对老板的回复和对朋友的回复在策略上没有系统性的区分。

### ExpressCoach 的方案
**规则词典 (0.3) + LLM 精调 (0.7) 混合架构**，先通过 32 种中文关系词典快速锚定，再将关系判断结果注入生成 prompt，实现"因人而异"的表达策略。

### 测试证据

**3 个场景 × 不同关系类型对比**:

| 场景 | 关系类型 | 亲密度 | 权力 | 利益 | 敏感度 | 生成策略调整 |
|------|---------|--------|------|------|--------|------------|
| 拒老板加班 | 上下级 | 一般 | 对方上位 | 强利益 | 高敏感 | 先肯定 + 请教口吻 + 留决策权 |
| 室友用东西 | 室友 | 较近 | 平等 | 弱利益 | 中敏感 | 直接温和 + 共同规则 + 维护关系 |
| 陌生人借钱 | 陌生人 | 疏远 | 平等 | 弱利益 | 低敏感 | 直接拒绝 + 简短 + 无需过多解释 |

**关键数据**:
- 4 维度准确率: **100%** (亲密度/权力/利益/敏感度各 10/10)
- 关系类型准确率: **100%** (10/10)
- 规则-LLM 混合在 100% 的场景中发挥了作用

**为什么通用 LLM 做不到**:
- ChatGPT 可以"理解"关系，但没有结构化的多维社交计算框架
- ExpressCoach 的关系词典是 **可审计、可扩展、可维护** 的知识工程产物，不是 prompt 中临时提示的几句话
- 混合权重机制 (规则 0.3 + LLM 0.7) 是系统设计选择，有明确的工程理由

## 不可替代点 3: 反应预测前瞻

### 问题
通用 LLM 只关注"我说什么"，不关注"对方会怎么反应"。

### ExpressCoach 的方案 (M5 预留 — 成员B 开发中)
基于关系模型的对方反应预测: 输入场景 + 关系判断 + 候选回复 → 预测对方可能的情绪反应、行为反应和对话走向。

### 设计理念
```
用户输入 → 意图识别 → 关系判断 → 三版本生成 → ★反应预测→ 用户选择
                                                      ↓
                                          "对方可能: 理解60% / 防御30% / 愤怒10%"
```

### 为什么通用 LLM 做不到
- 通用 LLM 的对话是单向的——只生成回复，不模拟对方
- ExpressCoach 的关系模型为反应预测提供了 **结构化先验**（亲密度/权力差/利益冲突程度决定了反应烈度）
- 这是 W3 多 Agent 沙盒的基础: Coach (教练) + Simulator (模拟对方)

## 不可替代点 4: 中文社交词典

### 问题
通用 LLM 对中文社交场景的理解依赖训练数据中的隐式知识，没有结构化的中文社交关系本体论。

### ExpressCoach 的方案
**32 种中文关系类型 × 3 维度标注** (intimacy/power/interest)，覆盖中国社会主要社交关系谱系。

### 词典结构
```json
{
  "type": "上级",
  "intimacy": "一般",
  "power": "对方上位",
  "interest": "强利益",
  "keywords": ["老板", "领导", "主管", "经理", "总监", "上司", ...],
  "typical_scenarios": ["汇报工作", "请假", "提建议", "拒绝加班", ...]
}
```

**覆盖范围** (32 种关系):

| 亲密度 | 数量 | 关系类型示例 |
|--------|------|------------|
| 亲密 | 5 | 父母、配偶、子女、兄弟姐妹、挚友 |
| 较近 | 9 | 好朋友、同事(关系好)、同学、室友、亲戚(近)、导师、晚辈、恋人、邻居(熟) |
| 一般 | 10 | 普通朋友、同事(一般)、上级、下属、老师、学生、合作伙伴、亲戚(远)、长辈(非家人)、网友、前同事 |
| 疏远 | 8 | 邻居(不熟)、客户、陌生人、服务人员、面试官/HR、专业人士、朋友的朋友 |

**每个条目包含**: keywords 关键词列表 + typical_scenarios 典型场景 + strategy 建议策略 + caution 注意事项

### 测试证据
- 10 个场景中规则词典命中率: **100%** (10/10 场景至少命中 1 个关系类型)
- 命中关键词平均: 2-3 个/场景
- 关系类型覆盖: 上级/室友/好朋友/客户/同事/陌生人/家人 — 全部在词典中有对应条目

### 为什么通用 LLM 做不到
- ChatGPT 没有结构化的中文社交关系知识图谱
- ExpressCoach 的词典是 **领域知识工程** 的产物，可以持续扩展和精调
- 词典作为规则层的输入，为 LLM 提供了 **可解释的决策锚点**（不是黑盒推理）

## 综合对比: ExpressCoach vs 通用 LLM

| 维度 | ExpressCoach | ChatGPT/GPT-4o |
|------|-------------|----------------|
| 输出模式 | 三版本并行 (温和+坚定+高情商) | 单一回复 |
| 策略分化 | Jaccard 自动检查 + 重试 (保证<0.7) | 依赖 prompt engineering |
| 关系感知 | 规则词典(32种×3维) + LLM混合 | 隐式理解，无结构化框架 |
| 生成依据 | 关系分析 → 策略调整 → 生成 | prompt 一次性描述 |
| 可解释性 | 每步输出 JSON + 推理过程 | 黑盒生成 |
| 可扩展性 | 词典可增补 + SOUL.md 可迭代 | 依赖 prompt 调优 |
| 中文优化 | 32种中文关系专门设计 | 通用多语言 |
| 成本 | DeepSeek (约 GPT-4o 的 1/5-1/10) | GPT-4o 定价 |

## 答辩 Q4 核心论述

> **Q: "你为什么不直接用 ChatGPT？"**
>
> **A:** "ChatGPT 是一个优秀的通用对话模型，但它在社交表达场景有三个根本局限：
>
> **第一，策略单一。** 它一次只能输出一种回复。用户需要反复 prompt 才能获得不同风格，而且无法保证风格差异度。我们的三版本并行架构用三份独立 SOUL.md 保证了结构性的策略分化，Jaccard 差异度平均 0.27，远低于 0.7 阈值。
>
> **第二，关系感知不足。** 对老板和对朋友的回复在策略上应该有系统性区分。我们构建了 32 种中文关系词典，配合规则+LLM混合架构，四维社交计算准确率达到 100%。
>
> **第三，缺乏社交计算框架。** 我们的系统不只是'写一段话'——它在做社交计算：意图分类 → 多维关系判断 → 策略选择 → 多版本生成 → (未来)反应预测。这是一个完整的社交智能 pipeline，不是单次 LLM 调用。
>
> 而且我们的成本约为 GPT-4o 的 1/5 到 1/10。"
>
> **数据支撑**:
> - 三版本 Jaccard 差异度平均 0.27（3 场景 × 3 组对比）
> - 四维关系判断准确率 100%（10 场景测试集）
> - 中文关系词典 32 种类型全标注
> - DeepSeek API 成本优势（约为 GPT-4o 的 1/5）
