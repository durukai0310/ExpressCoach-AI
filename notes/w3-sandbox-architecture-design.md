## 1. 多Agent协作方案调研

### 1.1 CrewAI

| 维度 | 评估 |
|------|------|
| **核心概念** | 角色驱动 (Role-Based): 每个 Agent 有明确的 Role/Goal/Backstory |
| **协作模式** | 顺序任务 (Sequential) / 层级任务 (Hierarchical) |
| **优势** | 角色定义清晰，任务编排简单，适合结构化工作流 |
| **劣势** | 缺乏实时对话交互能力；Agent 间通信是单向任务传递，非双向对话 |
| **ExpressCoach 适用性** | ⭐⭐⭐☆☆ — 角色定义部分可用，但沙盒需要的是实时对话而非任务链 |

### 1.2 AutoGen (Microsoft)

| 维度 | 评估 |
|------|------|
| **核心概念** | ConversableAgent: 每个 Agent 可以发送/接收消息，支持多轮对话 |
| **协作模式** | 双Agent对话 (Two-Agent Chat) / 群组对话 (GroupChat) |
| **优势** | 原生支持多轮对话，Agent 间可自由通信；支持 human-in-the-loop |
| **劣势** | 依赖 Python 生态；上下文管理需手动控制；对话终止条件需显式设计 |
| **ExpressCoach 适用性** | ⭐⭐⭐⭐☆ — 双Agent对话模式最适合沙盒场景 |

### 1.3 Meta CICERO (外交游戏AI)

| 维度 | 评估 |
|------|------|
| **核心概念** | 战略推理 + 自然语言生成: 一个 Agent 同时做"意图推理"和"对话生成" |
| **协作模式** | 单Agent 内部分层: 战略层 (what to say) → 执行层 (how to say) |
| **优势** | 战略与表达解耦；通过可控生成实现意图驱动的对话 |
| **劣势** | 游戏特化，非通用社交对话框架；需要大量训练数据和 RL 微调 |
| **ExpressCoach 适用性** | ⭐⭐⭐☆☆ — "战略层→执行层"的分层思想可借鉴，但不需要 RL |

### 1.4 调研结论

**ExpressCoach W3 沙盒的最佳技术路线: AutoGen 风格的双Agent对话 + CICERO 的分层思想**

- **为什么不是 CrewAI**: 沙盒需要实时双向对话，而非任务链
- **为什么借鉴 AutoGen**: 双Agent对话模式原生支持"教练旁听+适时介入"
- **为什么借鉴 CICERO**: 将"社交意图推理"和"回复生成"分层，教练Agent专注前者，模拟方Agent专注后者

## 2. ExpressCoach 沙盒 2-Agent 架构设计

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────┐
│                   ExpressCoach 沙盒                        │
│                                                         │
│  ┌─────────────┐    共享上下文     ┌──────────────────┐  │
│  │ 教练 Coach   │ ◄────────────► │ 模拟对方 Simulator │  │
│  │  (Meta-Agent) │   对话历史      │  (Role-Agent)      │  │
│  │             │   关系图谱       │                   │  │
│  │ 职责:       │   意图状态       │  职责:             │  │
│  │ · 监控对话   │               │  · 扮演对方角色     │  │
│  │ · 分析风险   │               │  · 生成对方回复     │  │
│  │ · 适时介入   │               │  · 模拟真实反应     │  │
│  │ · 提供建议   │               │  · 支持性格参数     │  │
│  └──────┬──────┘               └────────┬─────────┘  │
│         │                               │             │
│         │          ┌──────┐             │             │
│         └──────────┤ 用户  ├─────────────┘             │
│                    │(人类) │                            │
│                    └──────┘                            │
│                                                         │
│  对话流: 用户 ─→ Simulator ─→ 用户 ─→ Simulator ─→ ...  │
│  教练:   静默监控 ─→ (触发条件) ─→ 插入建议/警告         │
│                                                         │
│  最大轮次: 10 轮对话                                     │
│  上下文窗口: 共享对话历史 (最多10轮 × 2 = 20条消息)        │
└─────────────────────────────────────────────────────────┘
```

### 2.2 Agent 详细设计

#### Agent 1: 教练 Coach (Meta-Agent)

| 属性 | 值 |
|------|-----|
| **角色定位** | 社交表达教练 — 不是替用户说话，而是帮用户说得更好 |
| **系统Prompt核心** | "你是一位社交表达教练。你在旁听用户与对方的对话，但只在关键时刻介入。你的职责不是替代用户表达，而是帮用户理解社交结构、给出策略建议、在用户即将'踩坑'时提醒。" |
| **输入** | 对话历史 (全部) + 关系图谱 (从M2模块初始化) + 用户当前草稿 (如用户请求建议) |
| **输出** | 介入建议 (仅在触发条件满足时) 或 静默 (null) |

**介入触发条件 (仅关键时刻)**:

| 触发类型 | 条件 | 介入方式 |
|---------|------|---------|
| 用户求助 | 用户输入包含 "?" / "help" / "怎么办" / "帮我" | 主动分析当前局面 + 给出 2-3 个策略选项 |
| 语气风险 | 检测到用户输入包含攻击性/过分软弱/自相矛盾 | 警告 + 建议调整方向 |
| 对话僵局 | 连续 2 轮双方无实质推进 (重复/回避) | 分析僵局原因 + 给出破局建议 |
| 关系偏离 | 当前对话走向与初始关系定位严重不符 | 提醒用户回到目标轨道 |
| 轮次提醒 | 第 8 轮时 | 提醒对话接近上限，建议收尾 |

**不介入的场景**:
- 对话流畅进行中
- 用户表达自然且策略得当
- 模拟对方正常回应

#### Agent 2: 模拟对方 Simulator (Role-Agent)

| 属性 | 值 |
|------|-----|
| **角色定位** | 根据角色参数扮演对话中的对方 |
| **系统Prompt核心** | "你正在扮演'{角色}'。你的性格类型是'{性格类型}'。请根据你的角色设定和对话历史，自然地回应用户。你的回复应该真实反映这个人物的思维方式、情感反应和语言习惯。" |
| **输入** | 对话历史 (全部) + 角色设定 (关系类型/性格参数/当前情绪) + 用户最新消息 |
| **输出** | 对方回复 (自然语言) |

**模拟对方性格参数 (可调)**:

| 性格类型 | 特征 | 适用场景 |
|---------|------|---------|
| 友善型 | 理解、配合、积极回应 | 测试"关系维护"策略效果 |
| 中性型 | 理性、就事论事、不带情绪 | 测试"职场沟通"场景 |
| 刁难型 | 质疑、施压、不轻易退让 | 测试"坚定立场"策略韧性 |
| 回避型 | 不正面回应、转移话题、拖延 | 测试"催促"策略有效性 |
| 情绪型 | 反应激烈、感性化处理 | 测试"高情商"安抚效果 |

**角色真实性保障**:
- 每个性格类型有独立的 system prompt 模板
- 角色初始化时注入 M2 关系判断结果作为背景
- 模拟对方不会"知道"教练的存在（教练是旁听者）

## 3. 三个预判难点 + 对策

### 难点1: 上下文窗口管理 ⚠️

**问题**: 10 轮对话 = 20 条消息 + 系统 Prompt + 关系图谱 → 约 3000-5000 tokens。若用户消息较长或历史累积，容易超出模型上下文窗口。

**对策**:
- **滑动窗口**: 保留最近 6 轮对话 (12 条消息) + 摘要前 4 轮
- **分层摘要**: 每 3 轮对"关系状态变化"做一次摘要，注入后续上下文
- **降级策略**: 超过窗口上限时，自动压缩早期对话为 1-2 句摘要

### 难点2: 教练介入时机 ⚠️

**问题**: 介入太频繁 → 用户觉得被打断；介入太少 → 用户踩坑后才来补救。平衡"观察"和"介入"是核心挑战。

**对策**:
- **三级介入阈值**:
  - 🔴 紧急 (语气明显攻击性/自相矛盾): 立即介入
  - 🟡 关注 (对话走向偏离目标): 等当前轮结束后介入
  - 🟢 低优先级 (策略优化建议): 仅在用户主动求助时给出
- **冷静期**: 每次介入后至少等 2 轮才能再次介入 (用户求助除外)
- **介入记录**: 记录每次介入是否被用户采纳，用于调整介入策略

### 难点3: 模拟对方真实性 ⚠️

**问题**: LLM 扮演的"对方"可能过于理性/过于配合，缺乏真实社交中的非理性、情绪化、前后不一致等特征。

**对策**:
- **性格一致性**: 初始化时写入性格参数，每轮生成前注入"该性格类型的关键行为特征"
- **情绪演化**: 维护一个简单的情绪状态机 (友好→中性→不满→对抗)，根据对话内容更新
- **记忆偏差**: 每隔几轮注入一个微小的事实曲解 (模拟真实对话中的记忆偏差)
- **真实性打分**: 每轮对话后 Coach 静默评估 Simulator 回复的"真实性"分数，记录到日志

## 4. 10轮对话上限设计

### 4.1 为什么是 10 轮

| 考量 | 说明 |
|------|------|
| 上下文窗口 | 10 轮 × 2 条 × 平均 80 tokens/条 ≈ 1600 tokens，在安全范围内 |
| 实用价值 | 大部分社交场景的关键对话不超过 5-8 轮 |
| API 成本 | 10 轮约 15 次 API 调用 (用户 10 次 + Simulator 10 次 + Coach 介入 3-5 次)，约 $0.01-0.02 |
| 用户注意力 | 超过 10 轮的对话用户容易疲劳 |

### 4.2 终止条件

1. **正常结束**: 达到 10 轮上限 → Coach 总结对话 + 给出整体评价
2. **用户主动结束**: 用户输入 "/end" → 终止对话 + 总结
3. **目标达成**: Coach 判断用户已达成初始意图目标 → 提示是否可以结束
4. **对话崩溃**: 连续 3 轮检测到双方无法沟通 → Coach 介入建议重启

## 7. 答辩 Q5 素材

### 核心卖点

> "ExpressCoach 的 W3 沙盒不是简单的'让两个 AI 聊天'——我们设计了**非对称双Agent架构**：一个教练(Meta-Agent)旁听但不参与对话，只在关键时刻介入；一个模拟方(Role-Agent)扮演对话中的对方。这种设计模拟了真实社交教练场景：教练不会替你说话，而是帮你理解社交结构。"

### 不可替代性

1. **教练静默介入**: 不同于聊天机器人的"每轮必回"，教练只在 5 种关键时刻介入
2. **性格可调的模拟方**: 5种性格类型覆盖了真实社交中的主要对方类型
3. **社交结构感知**: 沙盒不是盲目对话，而是基于 M2 关系判断结果的关系图谱
4. **10 轮上限设计**: 基于成本和实用性的工程决策，非随意设定

### 已知局限 (诚实说明)

- ⚠️ 模拟对方仍基于 LLM，与真人的非理性/情绪化有差距 → 我们通过性格参数和情绪状态机尽量逼近
- ⚠️ 上下文窗口是硬约束 → 滑动窗口+分层摘要方案在 W3 实现
- ⚠️ 教练介入时机的"最佳阈值"需要大量用户测试 → W4 用户测试阶段持续调优
